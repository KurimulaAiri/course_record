## 一、后端异常体系（Spring Cloud 微服务）

### 1. 核心组件
- **业务异常**：`BusinessException`（继承 `RuntimeException`），携带 `ResultCode` 枚举码与动态消息，用于在 Service 层显式抛出业务错误。
- **状态码枚举**：`ResultCode`（SUCCESS/200、PARAM_ERROR/400、COURSE_BALANCE_NOT_ENOUGH/1001、STUDENT_ALREADY_IN_CLASS/1002、SYSTEM_ERROR/500）。业务代码通过 `throw new BusinessException(ResultCode.XXX, "动态消息")` 抛错。
- **全局异常处理器**：`GlobalExceptionHandler`（`@RestControllerAdvice`），集中捕获并转换为统一的 `ResponseDTO` JSON 响应，避免视图转发。

### 2. 已覆盖的异常类型及策略
- `HttpMessageNotReadableException` → HTTP 400，解析非法 JSON / 缺失请求体 / 字段类型不匹配 / 未知字段，提取具体字段名与期望类型返回友好提示。
- `MethodArgumentNotValidException` → HTTP 400，`@Valid` + `@RequestBody` 校验失败，聚合所有字段错误为 `字段 [name]: message` 列表。
- `ConstraintViolationException` → HTTP 400，`@Validated` + `@RequestParam/@PathVariable` 校验失败，取属性路径最后一段作为字段名。
- `BindException` → HTTP 400，Query/表单绑定失败，同上聚合字段错误。
- `BusinessException` → HTTP 200，使用 `e.getCode()` 作为业务码，消息透传；由前端根据业务码判断成功/失败。
- `DuplicateKeyException` → HTTP 409，按根因信息中的表名/索引名区分重复场景（学生课程重复、家长学生重复、用户平台重复等），返回具体原因。
- `DataIntegrityViolationException` → HTTP 400，外键约束失败，尝试从错误信息中抽取子表与字段名，给出“关联引用的上级数据不存在”的提示。
- `RuntimeException` → HTTP 500，兜底捕获未处理运行时异常，记录完整堆栈后返回“系统异常：message”。
- `HttpMediaTypeNotSupportedException` → HTTP 415，非 application/json 请求头拒绝。

### 3. 设计决策
- 业务异常一律返回 HTTP 200，由前端根据 `code` 字段判断，避免浏览器/网关对 5xx 做额外拦截。
- 数据库冲突与完整性异常不做 try-catch 下沉到 DAO，直接上抛由全局处理器统一映射为可读文案。
- 日志仅在全局处理器中 `logger.error(...)` 打印堆栈，业务层不自行打日志。

## 二、管理前端错误处理（Vue3 + Element Plus）

- **Axios 拦截器**（`src/utils/request.ts`）：
  - 请求拦截：自动注入 `Authorization: Bearer <token>` 以及签名头 `x-sign/x-timestamp/x-nonce`。
  - 响应拦截：
    - 401：优先判断是否为 refresh 请求本身；否则用 `admin_refresh_token` 调用 `/user/refresh` 续签，成功后重试原请求；续签失败则清空本地 token 并跳转登录页，同时防抖避免重复弹窗。
    - 其他 HTTP 错误：读取 `error.response.data.message/msg`，通过 `ElMessage.error` 展示；网络异常统一提示“网络异常，请检查网络连接”。
  - 所有错误最终 `Promise.reject(error)`，由调用方决定是否吞掉或进一步处理。

## 三、小程序端错误处理（UniApp）

- 各 API 模块（如 `src/api/auth/index.ts`）普遍采用 `try/catch` + `uni.showToast` 或直接 `reject(err)` 的模式，缺乏统一的拦截器封装；部分文件存在 Promise reject 与 resolve 混用的不一致写法。
- 通用工具 `src/utils/common/index.ts` 中使用 `uni.showToast` 展示错误提示，但样式与交互风格不统一。

## 四、MCP 运维 Server（Node.js）

- 当前仓库未发现专门的错误处理中间件或统一错误响应结构，API 层错误处理较为分散。

## 五、开发者应遵循的规则

1. **Service 层只抛 `BusinessException`**，不要直接抛 `RuntimeException` 或 `IllegalArgumentException`（后者仅在 auth-service 内部角色枚举分支中出现，建议也改为业务异常）。
2. **新增业务错误码**时先在 `ResultCode` 枚举中添加条目，再在对应 Service 处引用，禁止硬编码数字码。
3. **Controller 层不写 try-catch**，让全局异常处理器统一收敛；如需自定义特定 Controller 的错误格式，新建独立的 `@RestControllerAdvice` 类。
4. **管理前端**：不要在单个 API 调用处重复实现 401 刷新逻辑，全部交由 `request.ts` 拦截器处理；业务错误通过 `ApiResponse.code` 判断后再决定 `ElMessage` 提示内容。
5. **小程序端**：建议抽离统一的 `request/index.ts` 拦截器，集中处理 401、业务码错误与网络异常，消除各处 `try/catch` 与 `uni.showToast` 的散落实现。
6. **数据库约束错误**：若新增唯一索引/外键，需在 `GlobalExceptionHandler` 的对应 `@ExceptionHandler` 分支中补充友好文案，避免回退到“数据冲突”兜底消息。
